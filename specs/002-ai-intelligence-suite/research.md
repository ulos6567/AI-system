# Phase 0: Research & Decisions

**Feature**: AI 인텔리전스·처방형 운영 인사이트
**Date**: 2026-06-05
**Plan**: [plan.md](./plan.md)

본 문서는 Technical Context의 미해결 항목과 통합 패턴을 해소한다. Clarify 단계에서 확정된 3대 결정(시뮬레이션 데이터 / 외부 LLM / 처방 승인 필수)을 전제로 한다.

---

## R1. 처방형 액션 실행 경로

- **Decision**: 처방(`prescriptive_action`)은 항상 `proposed` 상태로 생성되고, 점주 승인 시에만 001의 기존 실행 서비스(`services/pricing.ts`, `services/auto-order.ts`)를 호출한다. 별도 자동 실행 경로를 만들지 않는다.
- **Rationale**: Clarify 결정(항상 점주 승인 필수, FR-003). 기존 검증된 실행 경로 재사용으로 중복·리스크 최소화. 승인이라는 단일 게이트로 감사(FR-027)가 단순해진다.
- **Alternatives considered**:
  - 신뢰도 임계치 초과 시 자동 실행 — Clarify에서 명시적으로 배제.
  - 처방 전용 별도 실행기 — 001 로직 중복 위험, 기각.

## R2. 처방 효과 자동 검증(Closed-loop)

- **Decision**: 처방 실행 시 대상 지표의 **베이스라인 스냅샷**(직전 동기간 평균: 매출·폐기·객단가)을 저장한다. 검증 기간(당일 마감 또는 7일) 경과 후 잡(`jobs/action-verify.ts`)이 실제 지표와 비교해 `action_outcome`을 생성하고, 적중 여부를 처방 유형별 추천 가중치에 반영한다.
- **Rationale**: 실행 시점 스냅샷이 있어야 사후 외부 변동과 무관하게 효과를 귀속할 수 있다(SC-002). 가중치 피드백은 단순 규칙으로 시작해 점진 개선 가능.
- **Alternatives considered**:
  - A/B 대조군 — 단일 점포 데모 환경에서 비현실적, 후속 과제.
  - 실시간 검증 — 단기 노이즈로 오판 위험, 기각.

## R3. LLM 경영비서 — RAG 오케스트레이션

- **Decision**: `services/assistant.ts`가 (1) 자연어 질의의 의도 분류 → (2) 해당 의도에 맞는 플랫폼 데이터 조회(매출·재고·예측 등) → (3) 비식별 근거 컨텍스트 구성 → (4) `llm` 포트로 외부 LLM 호출 → (5) 근거 출처(기간·데이터셋)와 함께 응답. 근거 데이터가 없으면 LLM 호출 없이 "데이터 없음"을 반환한다.
- **Rationale**: 근거 강제 + 폴백으로 환각률을 억제(SC-010, ≤2%). 의도 분류로 토큰·비용 절감. `llm` 포트 추상화로 모델 교체 가능(가역성).
- **Alternatives considered**:
  - LLM에 DB 직접 질의 도구 부여(function calling 무제한) — 통제·감사 어려움, 1차 기각.
  - 규칙기반/템플릿 — Clarify에서 외부 LLM으로 결정됨.
- **개인정보**: LLM 전송 컨텍스트에서 개인 식별자 제거(FR-026). API 키는 `.env`.

## R4. 시뮬레이션 데이터 공급(vision/anomaly/iot)

- **Decision**: 세 도메인 모두 기존 포트·어댑터 패턴을 따른다. 어댑터는 **시뮬레이션 구현**(시드 + 잡 기반 생성기)이며 포트 인터페이스는 실연동과 동일 형태로 정의한다. 동선/행동/센서/이상 이벤트는 날짜 상대 기준으로 생성(데모 신선도 유지).
- **Rationale**: Clarify 결정(시뮬레이션 데이터). 포트 동일성 덕에 후속 실연동은 어댑터 교체만으로 가능. 데모 환경에서 빈 화면 0건(SC-008) 보장.
- **Alternatives considered**:
  - 정적 픽스처만 — 시간 흐름·실시간 알림 데모 불가, 기각.
  - 실제 하드웨어 — 범위 외(Out of Scope).

## R5. 이상 알림 실시간 전달

- **Decision**: 001의 SSE 스트림(`routes/events.stream.ts`)과 `push` 포트를 재사용해 이상 이벤트를 30초 이내 전달(FR-014). 외부 관제 전파(FR-015)는 설정 기반 웹훅 어댑터로 추상화(1차 로그/모의).
- **Rationale**: 검증된 채널 재사용, 신규 실시간 인프라 불필요.
- **Alternatives considered**: WebSocket 신규 도입 — 단방향 알림엔 과함, 기각.

## R6. 인력 최적화 스케줄러

- **Decision**: 시간대별 수요 예측(001 forecast 재사용)으로 슬롯별 필요 인원을 산정하고, 직원 가용성·법정 제약(휴게·연속근무·주간 한도)을 만족하는 시프트를 **그리디 휴리스틱**으로 배정한다. 제약을 만족 못하면 위반 항목을 명시(FR-023).
- **Rationale**: 학기 범위에서 구현 가능한 결정론적 휴리스틱. 제약 위반 가시화로 안전(SC-011: 제약 100% 준수 또는 명시).
- **Alternatives considered**:
  - 정수계획법(ILP) 최적화 — 구현·의존성 과중, 후속 과제.

## R7. 히트맵·행동 분석 시각화

- **Decision**: 매대 그리드(존) × 체류 가중치 집계(`behavior_insight`)를 백엔드에서 산출하고 프론트에서 색상 그리드로 렌더. 행동 통계(관심·집었다 놓기)는 비식별 집계 테이블로 제공.
- **Rationale**: 클라이언트 렌더로 단순, 추가 라이브러리 최소화.

## R8. 데이터 보존·감사

- **Decision**: 처방 실행/AI 응답/이상 대응은 기존 `event_log` 감사 테이블을 확장해 100% 보존(FR-027, SC-012). 영상 분석은 비식별 집계만 저장, 식별 데이터 무동의 저장 0건(SC-013).
- **Rationale**: 단일 감사 경로 유지, 컴플라이언스 단순화.
